# Product fit and code audit: Wumpus Adventures (repo state at branch feat/gameplay-depth, Oct 2026)

Convention: statements about the repository cite relative file paths (and lines where noted) and were read directly from the code. Web claims carry URLs. Repo facts are "cited" to files rather than URLs.

## Q1. What does the game currently include, and what is missing versus commercial peers?

### Takeaway
The game is a clean, well-tested single-mode, score-chase "reveal-the-grid and collect gems" roguelite with 7 screens, 4 cosmetic characters, 6 entity types, a seeded generator, and a global Firestore top-10. It has no meta-progression, no daily/seed mode, no monetization, no analytics/crash reporting, no localization, almost no accessibility support, and no tutorial. Its "fairness" guarantee is reachability only, not deducibility (a no-guess guarantee does not exist).

### Cited Findings

#### Current product inventory (repo facts)
- Stack: Expo ~57.0.28, React Native 0.86.3, React 19.2.3, TypeScript ~6.0.3, zustand 5, firebase ^12.4, expo-audio, expo-haptics, expo-updates, React Navigation native-stack. Source: package.json. README.md says "Expo SDK 54" and PROJECT_OVERVIEW.md says "RN 0.81.4": both are stale versus package.json.
- Identity/config: app version 1.1.0, landscape-only, `userInterfaceStyle: light`, Android package `com.cuencaoscar.wumpusadventures`, no iOS `bundleIdentifier`, scheme `wumpus`, EAS project id and expo-updates URL set (app.json). eas.json: all three profiles use Android `buildType: apk` including `production`; `submit.production` is empty.
- Core loop: grid starts at 5x8 and grows to max 10x20; player starts at index 0 (top-left); goal is to collect all gems (3 at level 1, cap 8); levels repeat endlessly until death (src/core/difficulty/difficulty.ts L5-24; GAMEPLAY_SPEC.md).
- Entities: coin (gem), pit ("vortex": teleports player to an empty tile, preferring unexplored), enemy ("guardian": lethal, stationary), trap (hidden, -75 pts, non-lethal, from level 3, max 4), shield (absorbs one guardian hit, from level 2, carries across levels), ammo (+2 arrows, from level 2) (src/core/engine/types.ts L5; reducer.ts L147-201; difficulty.ts L17-21).
- Information model: hazards are hidden until visited; coins, shield and ammo are always visible (BoardView.tsx L105-111, L131-157). Visited tiles show a binary hint per hazard type (guardian icon, vortex icon) if any orthogonal neighbour holds that type; a number is shown only when two or more of the same type are adjacent (proximity.ts L17-41; BoardView.tsx L114-129). Hints are not shown on the tile itself or for diagonals. The hint says "one or more adjacent", not an exact count, below 2.
- Combat: ATTACK consumes 1 arrow, hits only the single adjacent tile in the facing direction; kill = 250 x combo (combo capped at 3, reset on any move); miss = -25 and combo reset (reducer.ts L232-271; src/config/gameConfig.ts).
- Scoring: step -1, new tile +5, coin 100 x level multiplier (1+0.2*(L-1)), level clear 500 x multiplier, power-up +50, score floored at 0 (scoring.ts; gameConfig.ts; reducer.ts L126, L209). Enemy combo is zeroed by every move (reducer.ts L223).
- Generation: seeded Lehmer/Park-Miller LCG (prng.ts, 16807 mod 2^31-1); safe zone is Manhattan radius 3 around spawn; hazards placed randomly, enemies avoid 2+ adjacent enemies; BFS check that every coin is reachable without crossing a lethal tile; up to 10 attempts, then hazards are relaxed and finally set to zero (generator.ts L42-122, L140-169). The seed passed in production is `Date.now()` for every reset and every level-up (useGameEngine.ts L16, L33), so a run is not reproducible from a single seed.
- Screens (src/navigation/StackNavigator.tsx): Cover (Play / Scores / Instructions / Settings), Characters (4 selectable heroes), Game, HighScores ("Champions Lineup"), LevelComplete (1-3 star rating: level done / all coins / >=50% enemies killed, per LevelCompleteScreen.tsx comment ~L37-40), Instructions ("Game Manual"), Settings (global sound toggle, control position left/right only, SettingsScreen.tsx L46-69).
- Characters are purely cosmetic: src/data/characters.ts has only sprite refs and an arrow colour; no stats (PROJECT_OVERVIEW.md claims "unique stats": inaccurate).
- Persistence: local `{bestScore, bestLevel, gamesPlayed}` in AsyncStorage key `wumpus.stats.v1` (src/services/localStats.ts; src/core/stats/runStats.ts); settings via zustand persist (src/state/settings/store.ts). Online: Firestore collection `highscores` with fields level, score, name (max 20 chars), coins, characterIndex, time; top-10 query then in-memory tie-break (src/services/highscores.ts L40-66; HighScoreEntryModal.tsx L58).
- Feedback/polish present: haptics at game over, kill, coin, trap, power-up, button press (useGameEngine.ts L45-85; DirectionPad.tsx L43, L81); event-bus audio with 3 music tracks and 7 SFX plus proximity loops for guardian/vortex ("hear" hazards) (src/audio/*; src/state/sound/store.ts L217-226); Animated-based move tween, board shake, danger vignette, score popups, coin flight.
- Engineering quality: pure deterministic reducer; Jest suite of 9 files / 137 tests, all passing when I ran `npx jest` (tests/engine/*). Stress test checks reducer invariants.
- Dead/unused infrastructure: telemetry is a single `console.log` (src/core/telemetry/telemetry.ts L1-3); replay recorder is an in-memory array that is never cleared in app code (src/core/replay/replay.ts; `clearActionHistory` has no callers) and grows with every move; the engine event emitter has no non-audio consumers visible in my grep. Spec docs call these "infrastructure" but they produce no player or business value today.
- Content gaps visible in code: Instructions screen text mentions "reach the extraction exit" (InstructionsScreen.tsx ~L225), but no exit exists in the engine. Docs/UX text is English only; no i18n library in package.json.

#### Missing versus commercial peers (absence verified by grep over src/ and package.json for: ads, purchase, IAP, analytics, crashlytics, sentry, i18n, ErrorBoundary, pause, accessibility)
- No pause, no run-save/resume; app has no AppState handling for backgrounding (GameScreen.tsx uses BackHandler only, L83-90).
- No daily challenge, no shareable seed, no game modes (single endless mode only).
- No meta-progression, unlocks, achievements, currency, or missions. "Gems" are score only.
- No monetization hooks (no ads SDK, IAP SDK, remove-ads).
- No analytics, crash reporting, remote config, or A/B tooling.
- No localization; no color-blind-safe hint design (hints distinguished by icon and a purple/yellow tint, BoardView.tsx L97), only 4 accessibilityLabel/Role usages in the whole src/ (CoverButton.tsx L65-67; DirectionButton.tsx L57-58).
- No tutorial beyond a static manual screen.
- Enemies/hazards are all stationary; only one non-lethal hazard (trap) and one lethal-teleport (vortex); there is one enemy sprite (Guardian_Enemy.png) and one tile style, so content variety is very low for a roguelite.
- No iOS identifiers or store assets (no bundleIdentifier in app.json).

#### External design evidence
- No-guess Minesweeper generators generally place mines, run a logical solver, and discard layouts that force a guess; the underlying problem is NP-complete so many candidates may be tried. Sources are largely commercial blogs, not peer-reviewed — [Minesweeper algorithm explained](https://minesweeper.now/blog/minesweeper-algorithm-explained-how-the-game-generates-fair-boards), [NP-completeness blog](https://minesweeper.now/blog/is-minesweeper-np-complete-the-mathematics-and-logic-behind-the-game). A Simon Tatham-style approach (generate, solve with backtracking, shift mines where the solver is stuck) was described by an anecdotal HN commenter — [HN thread](https://hn.svelte.dev/item/44480852).
- Hoplite shipped a daily Challenge mode where all players get the same very hard 3-floor dungeon with fixed abilities, unlimited retries, and a new one each day; a reviewer saw this as encouraging regular play — [TouchArcade](https://toucharcade.com/2015/05/18/hoplite-daily-challenge-update). A write-up on Spelunky's daily argues a shared seed creates community of play — [Playing Software: The ritual](https://playingsoftware.substack.com/p/the-ritual).
- Solo-dev write-ups show daily seeds and shareable seeds can be done with no server because a deterministic simulation reproduces a run from seed (+ inputs) — [Daily challenges and shareable seeds](https://solodevstack.com/blog/daily-challenges-shareable-seeds-no-server), [Deterministic simulation architecture](https://solodevstack.com/blog/deterministic-simulation-architecture-roguelike). These are blog posts, not primary data.
- Meta-progression: Supergiant describes Hades as returning the player to the hub with run upgrades removed but permanent skills purchasable over time, and cites Slay the Spire's Ascension as inspiration for the Pact of Punishment difficulty ladder — [Tom's Guide interview](https://www.tomsguide.com/uk/features/hades-exclusive-interview-supergiant). A roguelite design blog argues permanent upgrades should enhance run-to-run skill challenge, not trivialize it — [Bugnet](https://bugnet.io/blog/how-to-design-a-roguelite-meta-progression). Community opinion is split on whether Slay the Spire's Ascension counts as meta-progression ([lemmy thread](https://next.lemm.ee/comment/14156553)); this is opinion only.
- Rewarded video: vendors rank the post-death "revive/second chance" prompt as the lowest retention risk, highest opt-in placement, recommend 2-3 rewarded ads per session and opt-in only — [Applixir](https://www.applixir.com/?p=2833), [Brave Bits](https://bravebitsglobal.com/blog/rewarded-ad-strategy-players-love). Vendor claims of large session-length lifts (e.g. +16% / +211%, attributed to CookApps) are unverified vendor summaries. An independent-ish test by GameAnalytics found that doubling video ad exposure had negligible effect on retention and that watchers' better retention is correlation from engaged users — [GameAnalytics](https://www.gameanalytics.com/blog/rewarded-video-retention-impact-match-3-games).

### Inferences
- The generator's guarantee (BFS reachability over non-lethal cells, generator.ts L98-101) is weaker than "no-guess": a coin can be reachable yet the safe path may require stepping onto an unrevealed tile with no distinguishing hint. Because hints are binary below 2 neighbours and the first 3-radius is clear, forced guesses are very likely on denser late boards (levels with 10 pits and 12 enemies in 10x20). I did not run a solver to measure this; it is an unmeasured risk. Arrows (probe a facing tile) soften but do not remove it. Adding exact neighbour counts, or a deducibility check (a simple constraint solver run on the generated board), is the Minesweeper-peer way to make the difficulty feel fair.
- Because seeds come from `Date.now()` per level, a daily seed needs one tweak: derive each level seed from (dailySeed, level), e.g. `hash(dailySeed + level)`. The PRNG itself is deterministic and the reducer already avoids Math.random, so the architecture is well suited.
- The strongest unused asset is the deterministic reducer plus recorded actions: a (seed, action list) is already enough for replay and server-side score validation.
- The game's differentiators vs peers are weak today: the single-mode endless loop with 4 re-skins resembles a prototype; peers (Minesweeper clones, Hoplite-like, Desktop Dungeons-like) differentiate on daily modes, run variety, and progression.

### Gaps
- No retention/ARPDAU benchmarks specific to Minesweeper/Wumpus-style puzzle-roguelites were found; the searches returned vendor blogs and forum threads, not GDC data or postmortems with figures. No GDC talk on roguelite meta-progression was located.
- Did not retrieve primary Game Developer articles for Minesweeper no-guess generation; claims above rely on blogs.
- I did not measure how often generated boards force a guess (would need a solver; not written because repo files must not be modified).

## Q2. Which 8-12 features give the best retention/revenue return per unit of solo-dev effort, in order, with rough effort estimates?

### Takeaway
Ship measurement and safety first (analytics/crash, then secure leaderboard), then the retention loop that the existing deterministic engine makes cheap (daily seed, fairness, pause/resume, tutorial), then monetization (rewarded revive, remove-ads), then progression and content variety. Effort estimates below are my judgement for one developer; they are not sourced.

### Cited Findings
(Evidence behind the ranking is cited in Q1: daily seed — Hoplite/Spelunky; revive placement — vendor/GameAnalytics; meta-progression — Hades/Bugnet; no-guess — minesweeper.now.) Firebase App Check with Play Integrity works in Expo through `@react-native-firebase/app-check`, needs distribution through Play Store, must be initialized before Firestore, and enforcement should be enabled only after all app variants are registered; the JS SDK reCAPTCHA provider failed in an Expo project, so native RN Firebase is the working path — [RN Firebase App Check docs](https://rnfirebase.io/app-check/usage), [firebase-js-sdk issue 7060](https://github.com/firebase/firebase-js-sdk/issues/7060).

### Inferences
Prioritised backlog (impact on retention/monetization vs effort; days are rough solo-dev estimates):

1. Analytics + crash reporting + funnel events (2-3 days). Impact: enables every other decision; no revenue itself. Notes: replace `logGameEvent` (src/core/telemetry/telemetry.ts) with a provider call (Firebase Analytics / Sentry / PostHog); the event hooks already exist in useGameEngine.ts L43-93 (GAME_OVER, COIN, KILL, TRAP, POWERUP). Track: level reached at death, death cause, session length, D1/D7, tutorial drop-off. Add React error boundary at App.tsx root (see Q3). Using expo-dev-client native modules requires a new EAS build (runtimeVersion policy is appVersion).
2. Secure the leaderboard (2-4 days). Impact: protects the one social feature and store reputation. Notes: Firestore rules + Anonymous Auth + App Check; see Q3. Optionally validate with replay (item 4).
3. Daily seeded challenge with its own leaderboard (3-4 days). Impact: highest retention return per day of work (D1/D7 habit; Hoplite/Spelunky precedent); also drives share/virality. Notes: add `seedFromDate(utcDate)` -> `levelSeed = hash(dailySeed, level)`; pass seed into `generateBoard` in useGameEngine.reset/levelUp (L16, L33; currently Date.now()); fixed character and fixed loadout for fairness; one attempt or best-of-N; store `daily:{date}` result in AsyncStorage (pattern in localStats.ts); leaderboard collection `daily_{date}`; show streak counter on Cover.
4. Pause, save/resume run, and AppState handling (1-2 days). Impact: reduces churn from interrupted sessions; store reviewers expect it. Notes: serialize GameState (already plain data; entityMap derived) plus session timer to AsyncStorage; pause overlay in GameScreen; stop timer/audio on AppState background (useSessionTimer.ts and audio loops currently unmanaged).
5. Fair-board generation: exact neighbour counts + deducibility check (3-5 days). Impact: perceived fairness is the main churn driver in Minesweeper-likes; reviews complain about unfair deaths. Notes: option A: always show the exact number of adjacent hazards (proximity.ts already counts, BoardView hides count 1); option B: a lightweight solver in generator.ts that simulates safe reveals from spawn and rejects boards where no safe move exists; reuse the existing 10-attempt loop. Add a unit test in tests/engine/generator.test.ts.
6. Interactive first-run tutorial / guided level 1 (2-3 days). Impact: day-1 retention; the current manual (InstructionsScreen.tsx, 455 lines) is a static scroll. Notes: scripted seed with forced hint demonstrations; persist `tutorialDone` in settings store.
7. Rewarded-ad "revive" at game over (3-4 days, plus ad account setup). Impact: primary ad revenue for this genre; low retention risk per vendor sources; cap per run (e.g. one per run). Notes: hook into GameScreen game-over effect (L105-124) and show a "Continue" button in GameOverOverlay; need a reducer action `REVIVE` that clears isGameOver and moves the player to the previous safe tile or grants a shield; use `react-native-google-mobile-ads` (needs dev build/prebuild; not Expo Go) and UMP consent for GDPR. Add interstitial only at natural breaks if at all; the GameAnalytics evidence says more ad exposure does not help retention.
8. Remove-ads IAP + small cosmetic packs (3-5 days). Impact: second revenue stream; the typical purchase in this genre is a one-time remove-ads. Notes: RevenueCat (`react-native-purchases`) or expo-iap; entitlement in zustand persisted store; characters.ts is already a data array so cosmetic packs and hero skins are a content-only addition (the 4 heroes are currently free and stat-less).
9. Meta-progression and achievements (5-7 days). Impact: long-term retention. Notes: persistent "gems bank" (convert score or coins to currency in runStats.ts; extend LocalStats beyond 3 fields), unlock heroes with distinct perks (e.g. extra arrow, start shield, hint radius) which finally makes characters mean something; achievements list (reach level 10, kill 3-combo, no-arrow clear); keep permanent buffs small so skill still matters (Bugnet/Hades notes). Optional Firebase Auth + Firestore doc `users/{uid}` for cloud save.
10. Enemy variety and run structure (6-10 days). Impact: stops the loop becoming repetitive after 10-15 minutes. Notes: add a new `EntityType` (roaming guardian that moves 1 tile per N player moves; archer with line-of-sight; mimic coin) with reducer changes and extra turn step in MOVE; keep determinism using seed-derived pick (pattern pickDeterministic at reducer.ts L26-30); add biomes/tile skins every 5 levels, and a boss/exit every 5 levels to break endlessness; add mutators (modifiers) for the daily.
11. Localization ES/PT (+ FR/DE optional) (2-3 days for ES/PT) plus store listing localization. Impact: reach in LATAM markets (developer is Ecuador-based per email domain; assumption). Notes: extract strings (all UI is inline English, e.g. InstructionsScreen, GameOverOverlay) into `i18n-js`/`expo-localization`; the screens are text-heavy so Instructions is the largest cost.
12. Accessibility and audio/haptics polish (2-3 days). Impact: store quality bar, wider audience. Notes: color-blind-safe hints (unique shapes/patterns not just yellow vs purple tint, BoardView.tsx L97), add accessibilityLabel on tiles/HUD, haptics on/off and music/SFX sliders in SettingsScreen (only a single sound toggle exists), portrait/tablet layout is not offered (orientation locked to landscape), larger touch targets option.

Suggested release order: 1, 2, 4, 5 (hardening and fairness) then 3, 6 (retention) then 7, 8 (monetization) then 9-12. A minimal "v1.2 store-ready" bundle is 1-6 (about 13-20 days).

## Q3. What are the top technical and legal risks found in the code and assets?

### Takeaway
Top risks: (1) the Firestore leaderboard is client-writable by design with no rules file in the repo, so scores can be forged or the collection spammed; (2) there is zero crash/analytics and no error boundary; (3) audio and image assets have no recorded provenance or license, and several audio files are suspicious duplicates by size; (4) store-readiness gaps (APK production profile, no iOS id, no privacy policy artifacts, committed big debug files).

### Cited Findings

#### Firebase / leaderboard
- Firebase config with API key is hard-coded in src/lib/firebase.ts L4-11 (project id `mario-s-grid`, a different name from the game, suggesting a reused project). Google states Firebase API keys identify the project and are not secrets; access control is via Security Rules, which should default to deny — [Firebase security checklist](https://firebase.google.com/support/guides/security-checklist). So exposing the key is expected, but misconfigured rules would expose data.
- The repo contains no `firestore.rules`, `firebase.json`, or `.firebaserc` (git ls-files shows none), so the deployed rules cannot be audited from the repo; the client does `addDoc(collection(db,"highscores"), row)` with no auth (src/services/highscores.ts L68-77) and `getDocs` for reads (L40-66), which only works if rules allow unauthenticated read and create. Therefore the live rules are probably open for public create (inference; could not verify, they live in the Firebase console).
- Score payload is entirely client-supplied (score, level, coins, time, name, characterIndex; GameScreen.tsx L128-135). Time is clamped to >= 1 only (highscores.ts L72). Any client with the public key can POST arbitrary rows, including 999999999 scores, profanity names, or flood the collection. Rules can restrict fields/shape (allow-lists via `request.resource.data.keys().hasOnly([...])`, type/size checks) but cannot prove a score is legitimate — [Firebase data validation](https://firebase.google.com/docs/rules/data-validation), [Firestore rules fields](https://firebase.google.cn/docs/firestore/security/rules-fields). Real anti-cheat needs a trusted server (Cloud Function) or replay validation (inference; the web search did not retrieve a leaderboard-specific doc).
- App Check (Play Integrity) reduces use of the API key by non-genuine apps; it needs native `@react-native-firebase/app-check` in Expo and Play-distributed builds — [RN Firebase App Check](https://rnfirebase.io/app-check/usage). Not present in package.json.
- Leaderboard query reads `limit(20)` ordered by score (highscores.ts L43-47); every app launch calls prefetchLeaderboardThreshold (App.tsx L62), costing a Firestore read per launch per user; reads scale with DAU and are billable beyond the free quota (cost inference).
- The whole top-10 check is done client-side against a cached threshold (highscores.ts L22-38, L80-91), so the qualifier is trivially bypassable (server must re-check).
- Names are free text up to 20 chars (HighScoreEntryModal.tsx L58) shown publicly with no profanity filter; user-generated public text is a store-policy concern (inference).
- Privacy/legal: Firestore stores user-typed names plus device-independent data; no privacy policy, consent flow, or data-deletion path exists in the repo; Play requires a privacy policy and Data safety form for apps (general knowledge, not verified in my searches). Adding ads/analytics brings GDPR/UMP consent needs (general knowledge).

#### Missing instrumentation, crash handling, robustness
- No analytics or crash SDK in package.json; telemetry is console.log only (src/core/telemetry/telemetry.ts).
- No React error boundary anywhere (grep for ErrorBoundary/componentDidCatch returned no source hits). A render exception in BoardView/GameScreen would crash the app to the OS without recovery.
- Audio failures are swallowed with console.error (src/state/sound/store.ts L59, L117-162); the "Hammer Volume Loop" volume workaround (TECHNICAL_SPEC.md; store.ts L73-106) is fragile and device-dependent.
- Game-over check blocks on a network call: `isTopTenScore` awaits a Firestore fetch if the cached threshold is missing (highscores.ts L80-83; GameScreen.tsx L113-123), delaying the game-over overlay on slow networks; failure falls back to false, so offline works but the overlay can lag until fetch resolves/fails (inference on timeout behavior; Firebase JS SDK may retry offline).
- The in-memory action history grows unbounded each move (src/core/replay/replay.ts L4-11, called from useGameEngine.ts L29-32) and is never cleared; minor memory growth in long sessions.
- Timer/background: no AppState handling; timer and audio loops continue or desync after backgrounding (src/hooks/useSessionTimer.ts; GameScreen.tsx).
- Level-complete flow navigates to a separate screen then calls levelUp() 800 ms later in a timer effect (GameScreen.tsx L166-191); effect depends on `sessionTime`, which changes every second, so the effect re-runs and re-creates the timer (the cleanup clears the previous one) and could delay or double-fire in edge cases (reading of code; untested).

#### Performance
- BoardView renders every cell as an absolutely positioned `View` + `Image` (+ optional Animated hint overlays) via `.map` over rows*cols; max 10x20 = 200 cells, each with its own Animated.Value and potentially looping animation (BoardView.tsx L40-165, L240-257). The keys include the level, forcing a full remount of all cells every level (L246). Per-move, `getNearbyHazards` is recomputed for every visited cell and `visitedSet` is rebuilt each time `visited` changes; the reducer uses `state.visited.includes` (O(n)) and copies arrays/maps every move (reducer.ts L121-122, L16-19). At 200 cells these costs are small on modern phones but low-end Android could drop frames during pulse loops; GameScreen also calls `state.entities.filter(...)` in render (GameScreen.tsx L306) and recomputes enemy counts in effects. React Native docs recommend memoization/avoiding unnecessary re-renders for lists; I did not run profiling. Not a blocker at current grid sizes, but animated pulses on many hint cells simultaneously (one `Animated.loop` per hint cell) is the likely worst case.
- GameScreen reads `Dimensions.get("window")` once at module load (L39) and uses it for coin-flight start coordinates (L214-215), which breaks on rotation/foldables (landscape locked, so low risk).
- Image assets are large: icon, adaptive-icon, favicon are the same 1.1 MB file (identical md5 4326fc75..., assets/*.png), splash.png is 1.07 MB. A 1024px icon at 1.1 MB triples APK weight needlessly and `favicon` should be 48px. Release APK size not measured.

#### Build / store readiness
- eas.json production profile builds an APK; Play Store requires AAB for new apps (general knowledge; not verified in my searches). Set `android.buildType: "app-bundle"` for production (eas.json).
- Google Play: new apps and updates must target Android 16 (API 36) by Aug 31, 2026 (extension to Nov 1, 2026 possible) — [Android Developers target SDK page](https://developer.android.com/google/play/requirements/target-sdk). It is October 2026 now, so confirm the Expo SDK 57 native project targets API 36 (not verified in this audit; check android/build.gradle / expo-build-properties).
- No iOS bundle identifier, no iOS permission strings, no Apple developer metadata in app.json; `supportsTablet: true` while orientation is landscape-only.
- Large stray files tracked or present: `all_test_results.txt` (~4 MB) and `test_results.txt` exist at repo root (listed in .gitignore, so not tracked; present on disk); `android/` is gitignored but present locally (generated prebuild); `scripts/generateFeature.ts` and `src/core/specs/*` implement a spec/feature scaffolding generator inside the app source tree (src/core/specs/featureGenerator.ts, specRegistry.ts), shipping dev-tooling code in the app bundle (inference: they may be tree-shaken only if unused; imports not verified).
- Stale/contradictory docs: README says SDK 54; PROJECT_OVERVIEW.md says RN 0.81.4, "moving enemies", "unique character stats"; AI_PROJECT_CONTEXT.md has unfilled placeholders (`<PASTE OUTPUT HERE>`). A publisher doing due diligence would flag documentation drift.
